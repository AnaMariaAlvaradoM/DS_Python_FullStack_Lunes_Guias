Concepto · Un cliente HTTP central

Para qué existe

Cada petición con Axios lleva dos cosas: adónde va (la dirección del servidor más la ruta) y cómo va (encabezados, tiempo de espera, más adelante la prueba de quién la hace). Si cada función arma todo eso por su cuenta, esa información queda repetida en tantos lugares como funciones haya.

Mientras nada cambia, no duele. El día que cambia (el servidor se muda, o todas las peticiones deben llevar un dato nuevo), hay que encontrar cada copia. La que se olvide sigue con el valor viejo, y nada avisa: esa pantalla simplemente falla.

Qué es

Definición técnica

un cliente HTTP central es una instancia de Axios creada con axios.create(configuración), que guarda una configuración común (por ejemplo baseURL, la dirección base del servidor) y la aplica a todas las peticiones que se hacen con ella. Una instancia tiene los mismos métodos que axios (get, post, put, delete), y cada ruta que recibe se une a la baseURL. Se crea una vez, en un módulo propio, y se exporta para que los demás archivos la importen.

Explicación sencilla

en vez de escribir la dirección completa en cada petición, armas una sola vez "un Axios que ya sabe adónde ir", y a ese le pides solo la parte final: "/clases", "/reservas".

En la vida real: el domiciliario de confianza de un restaurante. No le dictas la dirección del restaurante cada vez que le pides algo: ya la sabe. Solo le dices qué traer. Si el restaurante se muda, se lo dices a él, una vez.

Míralo funcionar

Vas a verlo con una librería que pide sus libros y sus autores, en un ejemplo aparte del proyecto. Igual que en la Clase 3, cada ejemplo vive en su carpeta dentro de frontend/ejemplos/ y lo sirve el mismo npm run dev.

Cómo funciona por dentro

axios.create no hace ninguna petición: solo guarda la configuración. La petición ocurre cuando llamas api.get(…). En ese momento Axios mezcla dos configuraciones: la de la instancia y la de la llamada. Con los valores del ejemplo:

Esquema
api = axios.create({ baseURL: "/ejemplos/cliente" })   → guarda baseURL, no pide nada
api.get("/libros.json")
  configuración de la instancia  → baseURL = "/ejemplos/cliente"
  configuración de la llamada    → url = "/libros.json"
  dirección final                → "/ejemplos/cliente" + "/libros.json"
                                 = /ejemplos/cliente/libros.json
  el navegador la completa con el origen de la página → http://localhost:5173/ejemplos/cliente/libros.json

Dos reglas que permiten predecir cualquier caso:

  1. La configuración de la llamada gana sobre la de la instancia. Si una petición necesita algo distinto, lo pasa en la llamada y solo ella cambia.
  2. Una dirección absoluta ignora la baseURL. api.get("http://localhost:9999/otra") va a esa dirección. Por eso, dentro de un proyecto con cliente central, las peticiones solo llevan la parte final: si alguien escribe la dirección completa, se sale del cliente sin que nada avise.

La instancia es una sola en toda la aplicación aunque la importen diez archivos: JavaScript ejecuta cada módulo una vez y todos reciben el mismo objeto.

Cómo reconocerlo

Hazte esta pregunta: ¿hay algo que todas las peticiones a un mismo servidor comparten y que hoy está escrito en varias de ellas? La dirección, un encabezado, un tiempo de espera, una credencial. Si la respuesta es sí, ese algo pertenece a un cliente central y no a cada petición.

La prueba al revés también sirve: si para cambiar la dirección del servidor tienes que abrir más de un archivo, falta el cliente central.

En la tienda en línea aparece algo útil: dos clientes. Uno para la API de la tienda y otro para la de pagos, porque son servidores distintos con direcciones distintas. "Un cliente central" significa uno por servidor, no uno para todo el universo.

Cuándo centralizar y qué no guardar en el entorno

Cerrar el concepto evita convertir una herramienta útil en una regla ciega.

Límites · Un cliente HTTP central

Cuándo no usarlo

Un cliente central es por servidor. No lo uses para servidores que no son el tuyo, y no metas en él configuración que solo necesita una petición: eso va en la llamada (cliente.get("/x", { timeout: 2000 })). En un ejercicio de una sola petición a un archivo, como el de las frutas de la Clase 3, crear una instancia no aporta nada.

Con qué se confunde

Con una constante que guarda la dirección, como URL_API en la Clase 3. Las dos evitan escribir la dirección muchas veces, pero no hacen lo mismo:

Constante URL_APICliente axios.create
Qué guardaUn textoUna configuración completa (dirección, encabezados, tiempo de espera)
Quién arma la direcciónCada función, con ` ${URL_API}/clases `El cliente, solo
¿Puede agregar algo a todas las peticiones?NoSí: es su trabajo
¿Dónde se escribe axios?En cada archivo que pide datosSolo en cliente.js

El punto donde chocan: el token del Módulo 2. Con la constante, cada una de las cuatro funciones tendría que agregar el encabezado del token a mano. Con el cliente, se agrega una vez.

También se confunde .env con un lugar para secretos. En un backend, el .env sí guarda contraseñas, porque el código corre en el servidor y nadie lo ve. En Vite, todo lo que empieza con VITE_ termina dentro del JavaScript que descarga cualquier visitante. Un .env de frontend es configuración pública.

Variantes y casos límite

Un .env por modo. Vite también lee .env.development (con npm run dev) y .env.production (con npm run build), y el del modo gana sobre .env. Así, la dirección de producción puede vivir en .env.production y la de tu computador en .env. Publicar PulsoFit no es tema de este módulo; basta con saber que existe.

Un valor que no es texto. Todas las variables llegan como texto. Si algún día pones VITE_TIEMPO_ESPERA=5000, en el código llega "5000" y tienes que convertirlo con Number(import.meta.env.VITE_TIEMPO_ESPERA).

Errores frecuentes

Olvidar el prefijo VITE_. Es el 🔬 Quítala y mira del paso 2 de cliente.js: la variable no llega, la baseURL queda undefined y la petición va al propio Vite, que devuelve una página HTML. El síntoma no apunta al .env: clases.map is not a function. Cuando una lista "se rompe" justo después de tocar configuración, revisa el .env primero. Una forma rápida de comprobarlo: en la pestaña Network, la petición sale a localhost:5173/clases en lugar de localhost:8000/clases.

Crear el .env en la carpeta equivocada. Si queda dentro de src/ o en la raíz de pulsofit-fullstack/, Vite no lo lee: mismo síntoma que el anterior. Va al lado de package.json.

Guardar el .env y no recargar. Vite se reinicia solo, pero la pestaña que tenías abierta sigue con el código viejo hasta que recargas.

Escribir la dirección completa en un servicio. cliente.get("http://localhost:8000/clases") funciona, pero ignora la baseURL: el día que cambie el .env, esa petición seguirá yendo al lugar viejo. La regla: dentro de los servicios, solo la parte final.

En un sistema real

En el Módulo 2, PulsoFit tendrá inicio de sesión. Al ingresar, el backend entregará un token: un texto firmado por el servidor que prueba quién eres, como la manilla de un evento. El frontend lo guardará, y cada petición siguiente tendrá que llevarlo en un encabezado para que el backend sepa de quién son "Mis reservas". Gracias a lo que hiciste hoy, ese "cada petición" se resuelve en un solo archivo: cliente.js. Ninguna página ni servicio tendrá que cambiar.

Ya conocías los servicios de la Clase 3: separaban el "qué pedir" de las páginas. Hoy fuiste un paso más allá: el "adónde y cómo" salió de los servicios a un cliente central, y la dirección salió del código a la configuración. 07 · Concepto 2 · Comprender

Traducir la forma del error una sola vez

Una función pura separa el lenguaje técnico del mensaje para la persona.

Concepto · Errores traducidos en un solo lugar

Para qué existe

Cuando una petición falla, Axios entrega un objeto de error con información técnica: si hubo respuesta o no, el código de estado (404, 409, 500), el cuerpo que mandó el servidor. Esa información no le sirve a la persona que usa la aplicación: "Request failed with status code 404" no le dice qué hacer.

Alguien tiene que traducir. Si cada pantalla traduce por su cuenta, el mismo problema termina con frases distintas, y una regla nueva (por ejemplo, cómo avisar que el servidor está caído) hay que copiarla en cada catch de cada página.

Qué es

Definición técnica

un manejo de errores centralizado es una función pura que recibe el objeto de error de una petición y devuelve el mensaje para la persona, tomando la decisión según la forma del error: si no hay error.response, el servidor no respondió; si la hay, error.response.status dice qué pasó, y error.response.data trae lo que el servidor explicó. Cada catch de la aplicación la llama en lugar de escribir su propio mensaje.

Explicación sencilla

una sola función recibe "lo que salió mal" y responde "lo que le decimos a la persona". Todas las pantallas le preguntan a ella.

En la vida real: el intérprete de un hospital. Los médicos dicen "contusión", "hematoma", "fractura". El intérprete lo convierte en algo que el paciente entiende, y lo dice igual sin importar qué médico habló.

Míralo funcionar

Vas a verlo con errores simulados: objetos con la misma forma que los que entrega Axios. Como la función no necesita navegador ni servidor, se ejecuta con Node desde la terminal. Dentro de frontend/ejemplos/ crea la carpeta errores y dentro el archivo traductor.js.

Qué errores traduce esta función y cuáles no

Los fallos de red no son los mismos que los errores al renderizar.

Límites · Errores traducidos en un solo lugar

Cuándo no usarlo

El traductor central sirve para lo que es igual en todas partes. No lo uses para:

  • Validar antes de enviar. Eso ya lo hace validarReserva (Clase 2), sin pedirle nada al servidor. El traductor solo entra cuando el servidor ya respondió (o no).
  • Decidir qué hace la pantalla. El traductor dice qué decir, no qué hacer. Si un 409 debe además ocultar el formulario, esa decisión sigue en la página (como errorReserva en DetalleClase).
  • Errores que no vienen de una petición. Un error de programación (un nombre mal escrito) no es un problema del servidor; traducirlo esconde el error en vez de arreglarlo.

Errores frecuentes

Olvidar el import. Es el paso 1 de Clases.jsx: con el backend encendido todo funciona, y el error solo aparece cuando algo falla, como mensajeDeError is not defined y una pantalla en "Cargando…" sin fin. Por eso cada cambio de un catch se prueba con el backend apagado.

Dejar catch { sin el paréntesis. Si cambias la línea de adentro a mensajeDeError(falla) pero dejas catch {, la variable falla no existe: el mensaje es falla is not defined, con el mismo síntoma.

Preguntar por status antes de saber si hubo respuesta. Es el 🔬 Quítala y mira del traductor: Cannot read properties of undefined (reading 'status'). La pregunta por response siempre va primero.

Usar el traductor para un error que no es de red. Si dentro del try hay un error de programación (por ejemplo, datos.map cuando datos no es una lista), ese error tampoco tiene response, y la persona lee "No pudimos conectar con el servidor" aunque el servidor esté perfecto. Si ves ese mensaje con el backend encendido, abre la consola: el error real está ahí.

En un sistema real

Una aplicación en producción, además de mostrar la frase, registra el error técnico (con la hora, la página y el código) en un servicio de monitoreo, para que el equipo se entere sin esperar a que alguien se queje. Ese registro también iría en un solo lugar: dentro del traductor o junto a él. Y con el login del Módulo 2 llegará un caso nuevo, el 401 ("tu sesión terminó"), que además de la frase llevará a la persona a /login. Se agrega en este mismo archivo.

Conexión

En la Clase 3 cada página aprendió a decir "cargando" y "falló". Hoy la forma de decir "falló" quedó en un solo lugar, separada de las páginas, igual que la dirección del servidor quedó en el cliente. Valeria ya tiene su segundo punto: el sistema habla igual en todas partes. Falta el tercero: el menú no dice en qué sección estás, y el marco de todas las páginas sigue mezclado con la tabla de rutas en App.jsx.

Comprueba

El servidor responde 404 si el médico no existe, 409 si el horario ya está tomado (con un detail como "Ese horario ya fue asignado") y, a veces, no responde. ¿Qué casos tendría su traductor, cuáles frases escribe el frontend y cuál viene del servidor?

Ver respuesta

11 · Concepto 3 · Comprender

Un marco estable con un espacio para cada página

Una revista aislada hace visible el trabajo de una ruta de layout.

Concepto · Layout compartido con rutas anidadas

Para qué existe

Casi todas las aplicaciones tienen un marco: encabezado, menú y pie de página que no cambian, y en el medio un hueco donde va la pantalla de turno. Hasta ahora lo resolvías poniendo el marco alrededor de <Routes>: sirve mientras todas las pantallas tengan el mismo marco.

El día que un grupo de pantallas necesita otro marco (o ninguno), o que un grupo necesita una regla en común (por ejemplo, "solo para quien inició sesión"), ese arreglo ya no alcanza: el marco está pegado a toda la aplicación y la tabla de rutas no sabe que existe.

Qué es

Definición técnica

una ruta de layout es un <Route> sin path, con un element, que envuelve a otras rutas (sus rutas hijas, anidadas entre su apertura y su cierre). Cuando la dirección coincide con una hija, React Router pinta el elemento del padre, y el padre decide dónde va la hija poniendo el componente <Outlet />. Como no tiene path, no agrega nada a la dirección: /deportes sigue siendo /deportes (documentación de React Router, "Layout Routes").

Explicación sencilla

escribes el marco una sola vez, como una ruta más, y le dejas un hueco con <Outlet />. Las páginas que van dentro de ese marco se escriben adentro de esa ruta. React Router mete la página que toca en el hueco.

En la vida real: un portarretratos con vidrio intercambiable. El marco es el mismo; lo que cambias es la foto del medio. Y si una foto va sin marco (la que pegas en la nevera), simplemente no la metes en el portarretratos.

Cómo funciona por dentro

React Router no pinta "una ruta": pinta la cadena que lleva hasta ella. Cuando la dirección cambia, busca la ruta que coincide y después recorre hacia arriba sus padres. Pinta el más externo, y cada <Outlet /> deja pasar al siguiente.

Esquema
dirección: /deportes
  ¿qué ruta coincide?         → <Route path="/deportes">, hija de <Route element={<Marco />}>
  cadena a pintar             → Marco → <p>Resultados del fin de semana</p>
  se pinta Marco
    su <Outlet />             → <p>Resultados del fin de semana</p>

dirección: /imprimir
  ¿qué ruta coincide?         → <Route path="/imprimir">, sin padre
  cadena a pintar             → <p>Noticias de hoy, sin menú ni pie de página.</p>

Y al navegar de / a /deportes, el marco es el mismo en las dos: React no lo vuelve a crear, solo cambia lo que hay en el hueco. Por eso un layout puede guardar estado (por ejemplo, un menú abierto) que no se pierde al cambiar de sección.

Cómo reconocerlo

Pregúntate: ¿hay un grupo de pantallas que comparten algo que no es su contenido (el mismo encabezado, el mismo menú lateral, la misma regla de acceso)? Si sí, ese algo es un layout, y esas pantallas son sus hijas. Si todas las pantallas lo comparten y siempre lo harán, también es un layout, aunque sea uno solo.

Parte 2 · Un menú que dice dónde estás

Necesario para implementar · NavLink. NavLink es un Link de React Router que sabe si está activo: si la dirección actual coincide con su to, agrega a su <a> el atributo aria-current="page" (que los lectores de pantalla anuncian como "página actual") y permite elegir clases distintas para el caso activo. En className se le puede pasar una función en lugar de un texto: React Router la llama con un objeto que trae isActive (true o false) y usa como clases lo que la función devuelva (documentación de React Router, "Navigating"). Un NavLink está activo en su dirección y también en las que empiezan por ella: el de /clases queda activo en /clases/3. Si quieres que solo esté activo en la dirección exacta, se le agrega end. Sin NavLink, tendrías que leer la dirección tú mismo y comparar en cada enlace.

Cuándo un layout ayuda y cuándo sobra

El cierre conecta el patrón con aplicaciones más grandes.

Límites · Layout compartido con rutas anidadas

Cuándo no usarlo

Un layout es para lo que envuelve a varias pantallas. No lo uses para un pedazo que aparece en una sola (eso es un componente), ni para decidir algo que cambia dentro de la misma pantalla (eso es estado). Y si una aplicación tiene una sola pantalla, no necesita ni React Router ni layout.

Con qué se confunde

Con un componente que envuelve usando children, como Tarjeta en la Clase 2. Los dos dejan un hueco, pero lo llena alguien distinto:

Componente con childrenRuta de layout con <Outlet />
Quién llena el huecoQuien lo usa, escribiendo algo entre sus etiquetasReact Router, según la dirección
Dónde se declaraDentro de otro componente (<Tarjeta>…</Tarjeta>)En la tabla de rutas (<Route element={<Layout />}>)
Sirve paraPiezas visuales repetidas dentro de una pantallaEl marco de un grupo de pantallas

El punto donde chocan: podrías escribir <Layout><Clases /></Layout> en cada ruta usando children, y se vería igual. Pero tendrías que repetirlo en cada fila de la tabla, y la tabla dejaría de mostrar qué páginas comparten marco. Con Outlet, el agrupamiento se ve en la tabla.

Link y NavLink también se confunden: usa NavLink solo en menús, donde importa marcar la sección. En un botón "Ver y reservar" o en "← Todas las clases", un Link basta.

Variantes y casos límite

Dos layouts. Una aplicación puede tener varias rutas de layout hermanas: por ejemplo, un LayoutPublico para inicio y clases, y un LayoutAdmin con menú lateral para el panel de Valeria. Cada grupo de rutas va dentro del suyo, igual que /imprimir iba afuera del marco de la revista.

Una ruta de layout dentro de otra. Las rutas de layout se pueden anidar: dentro del Layout general, un segundo layout sin path para las páginas que exigen haber iniciado sesión. Es justo lo que se usará en el Módulo 2 para proteger /mis-reservas.

Errores frecuentes

Olvidar <Outlet />. Es el 🔬 Quítala y mira del Layout: el marco aparece y las páginas no, sin ningún error en la consola. Si "todas las páginas se ven vacías al mismo tiempo", revisa el Outlet.

Dejar el marco también en App. Si creas el Layout pero no quitas el div, Encabezado y PiePagina de App, ves el encabezado dos veces. Cada pieza del marco debe estar en un solo lugar.

Poner una ruta fuera del layout sin querer. Si escribes /login debajo del </Route> que cierra el layout, la página sale sin menú. Funciona, pero no era la intención. Mira la sangría de la tabla: las hijas van un nivel más adentro.

NavLink is not defined o className con texto fijo. Es el paso 1 del encabezado. Y si a NavLink le pasas className="font-bold" (un texto), todos los enlaces se ven iguales: la función es lo que permite distinguir el activo.

En un sistema real

En una aplicación grande, la tabla de rutas suele tener varios layouts y varios niveles: el público, el de la cuenta de la persona y el de administración, cada uno con su menú y sus reglas de acceso. Mantener el marco como ruta (y no como un div alrededor de todo) es lo que permite agregar esos niveles sin reescribir las páginas. Y NavLink con aria-current no es un adorno: hace que un lector de pantalla diga "Clases, página actual", que es parte de que una aplicación sea accesible.

Conexión

En la Clase 3 cada pantalla recibió su dirección. Hoy la tabla de rutas también describe cómo se agrupan: un marco con todas las páginas adentro, con App dedicado solo a eso, y un menú que sabe dónde estás. Con esto, Valeria tiene sus cuatro puntos: la dirección del servidor en un solo lugar, el sistema que habla igual, el menú que marca la sección y la pantalla de ingreso. Lo que viene es que esa pantalla funcione: el login con JWT del Módulo 2, que se apoyará en cliente.js y en esta tabla de rutas.
