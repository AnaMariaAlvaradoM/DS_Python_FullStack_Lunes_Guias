Concepto · estado

React necesita saber qué cambió

3.1 · Para qué existe

Una pantalla es una foto de los datos en el momento en que se dibujó. Si después el dato cambia y nadie vuelve a tomar la foto, la pantalla muestra algo que ya no es cierto.

En JavaScript sin librerías, cada vez que un dato cambiaba tenías que llamar a mano a una función que redibujara (como renderizar() en la Clase 0). Si se te olvidaba en un solo lugar, la pantalla mentía y nada te avisaba. React existe en buena parte para quitarte ese trabajo: tú le dices qué dato cambió y él redibuja. Pero para eso el dato tiene que estar en un lugar que React conozca.

3.2 · Qué es

  • Definición técnica: el es la memoria de un componente: datos que React guarda entre una pintada y la siguiente y que, al cambiar, hacen que React vuelva a ejecutar el componente y actualice la pantalla. Se crea con el Hook useState(valorInicial), que devuelve un par: el valor actual y una función para cambiarlo (const [valor, setValor] = useState(inicial)).
  • Explicación sencilla: useState es una caja que React cuida. No cambias la caja por dentro: le entregas a React el valor nuevo con setValor. Al recibirlo, React vuelve a dibujar el componente con ese valor.
  • En la vida real: el tablero de turnos de un banco. Si el cajero anota el siguiente turno en su cuaderno, el tablero no cambia y la gente sigue esperando. Si lo marca en el tablero, todos lo ven. setValor es marcarlo en el tablero.

3.6 · Cómo funciona por dentro

Esto es lo que pasó en el paso 3, en orden:

  1. La primera vez, React ejecuta Contador. useState(0) guarda 0 en la memoria de ese componente y devuelve [0, setVasos]. React dibuja "Vasos de agua hoy: 0".
  2. Haces clic. tomar llama setVasos(1). React no cambia vasos en ese instante: anota "en la próxima pintada, el valor es 1" y programa una nueva pintada.
  3. React vuelve a ejecutar toda la función Contador. Esta vez useState(0) ignora el 0 inicial y devuelve el valor guardado: 1.
  4. React compara lo que devolvió el componente con lo que hay en pantalla y cambia solo lo distinto: el número del párrafo.
Fragmento
Pintada 1   vasos = 0   → pantalla: "Vasos de agua hoy: 0"
Clic        setVasos(0 + 1)  → React programa otra pintada
Pintada 2   vasos = 1   → pantalla: "Vasos de agua hoy: 1"
Clic        setVasos(1 + 1)
Pintada 3   vasos = 2   → pantalla: "Vasos de agua hoy: 2"

Un detalle decide mucho: para saber si algo cambió, React compara el valor nuevo con el anterior usando Object.is. Con un número es fácil (1 no es 0). Con un arreglo o un objeto, compara si es el mismo arreglo, no su contenido. Si cambias un arreglo por dentro y le entregas el mismo, React concluye "no cambió nada" y no pinta. Por eso con estado siempre se entrega un arreglo nuevo.

3.7 · Cómo reconocerlo

Pregúntate: ¿este dato cambia mientras la persona usa la página, y la pantalla debe mostrar el cambio? Si las dos respuestas son sí, es estado y va en useState. Si el dato no cambia (el nombre de la empresa) o se puede calcular a partir de otro estado (cuántos elementos tiene una lista), no es estado.

Límites · estado

Guardar solo lo que realmente cambia

5.1 · Cuándo no usarlo

No todo lo que se muestra es estado:

  • Datos que no cambian mientras la página está abierta (el nombre del gimnasio, el texto del pie de página): una constante o una prop alcanzan.
  • Lo que se puede calcular a partir de otro estado (cuántas reservas hay, cuál es la clase elegida a partir de su id): se calcula en cada pintada, no se guarda.
  • Un dato que solo vive dentro de un clic y no se muestra: una variable normal dentro de la función alcanza.

5.2 · Con qué se confunde

Con una variable normal dentro del componente.

¿Cambiarla avisa a React?NoSí, con la función set…

El punto donde chocan es el paso 2 del contador: las dos "funcionan" en la consola. La diferencia solo se ve en la pantalla.

5.3 · Variantes y casos límite

  • El valor nuevo a partir del anterior. Si un mismo clic necesita cambiar el estado dos veces seguidas, setVasos(vasos + 1) dos veces suma uno, porque las dos usan el vasos de esta pintada. La forma con función, setVasos((anterior) => anterior + 1), recibe siempre el último valor y suma dos. Hoy no hace falta: cada clic cambia una sola vez.
  • Varios estados en un componente. Cada llamada a useState es una caja distinta. App va a terminar con tres.

5.4 · Errores frecuentes

  • Uncaught ReferenceError: useState is not defined (pantalla en blanco). Se lee: "no sé qué es useState". Causa: falta el import. Es el error del paso 4.
  • La pantalla no cambia y no hay error. Causa: cambiaste el arreglo por dentro y le entregaste el mismo a set…. Es el 🔬 del paso 6.
  • El valor "llega tarde" en la consola. console.log(listaClases) justo después de setListaClases(...) muestra el valor viejo: el nuevo existe recién en la siguiente pintada. No es un error.
  • Too many re-renders. React limits the number of renders to prevent an infinite loop. Causa: llamar set… directamente al dibujar, por ejemplo onClick={tomar()} con paréntesis. Se corrige entregando la función sin ejecutarla.

5.5 · En un sistema real

Hoy el estado vive en el navegador de cada persona: si Valeria y un cliente abren PulsoFit, cada uno ve sus propios cupos, y al recargar todo vuelve al inicio. En un sistema real el cupo verdadero lo tiene el servidor, y el estado de React es una copia para mostrarlo. Eso llega en la Clase 3.

5.6 · Conexión

Las props de la Clase 1 llevan datos hacia abajo; el estado es de donde salen. El estado de las clases quedó en App porque es quien decide. El siguiente concepto responde una pregunta que ya apareció: cuando varios componentes necesitan el mismo dato, ¿dónde debe vivir?

Un solo estado, varias piezas

6.1 · Para qué existe

En cuanto una pantalla tiene varias piezas, aparece la pregunta de quién guarda cada dato. La tentación es guardarlo en la pieza más cercana al clic. Funciona mientras una sola pieza lo necesita.

El problema llega cuando dos piezas muestran o cambian el mismo dato. Si cada una tiene su copia, cambiar una no cambia la otra, y la pantalla termina diciendo dos cosas distintas a la vez. Además, una pieza que guarda datos y decide qué hacer con ellos ya no se puede reutilizar en otro lugar donde la decisión sea distinta.

6.2 · Qué es

  • Definición técnica: separar lógica de presentación es repartir dos papeles entre los componentes. Un componente contenedor guarda el estado y decide qué pasa. Los componentes de presentación reciben datos por props, los muestran y avisan lo que ocurrió llamando funciones que también reciben por props. Cuando dos componentes necesitan el mismo dato, el estado se sube al ancestro común más cercano y desde ahí baja a los dos ("levantar el estado").
  • Explicación sencilla: hay un solo responsable que tiene los datos y toma las decisiones. Los demás son ventanillas: muestran lo que el responsable les da y, cuando alguien hace algo, le avisan. Ninguna ventanilla cambia los datos por su cuenta.
  • En la vida real: en una cocina de restaurante, la comanda la tiene el jefe de cocina. Los meseros toman pedidos y se los entregan; los cocineros leen lo que les asignan. Si cada mesero llevara su propia lista de lo que falta, dos platos saldrían para la misma mesa y uno nunca.

6.6 · Cómo funciona por dentro

En React los datos solo viajan hacia abajo, de padre a hijo, por props. Un hijo no puede cambiar las props que recibe. Para que un hijo "suba" algo, el padre le pasa una función; el hijo la llama, y como esa función se escribió dentro del padre, cambia el estado del padre.

Fragmento
Habitacion (estado: encendida = false)
 ├─ Bombillo     ← encendida = false              → "Luz apagada"
 └─ Interruptor  ← encendida = false, onCambiar   → "Encender"
Clic en Interruptor → onCambiar() → setEncendida(true)   (estado de Habitacion)
React vuelve a ejecutar Habitacion y a sus dos hijos con el valor nuevo:
 ├─ Bombillo     ← encendida = true               → "Luz encendida"
 └─ Interruptor  ← encendida = true               → "Apagar"

Como los dos hijos leen el mismo estado en la misma pintada, nunca pueden estar en desacuerdo.

6.7 · Cómo reconocerlo

Hazte dos preguntas:

  1. ¿Qué componentes necesitan este dato? El estado vive en el ancestro común más cercano de todos ellos.
  2. ¿Este componente decide o solo muestra? Si solo muestra, recibe datos y funciones por props y no guarda el estado de otros.

Límites · responsabilidades

Subir solo lo que varios necesitan

8.1 · Cuándo no usarlo

La regla corta: el estado vive lo más cerca posible de quien lo usa, y sube solo cuando varios lo necesitan. Cuando el ancestro común queda muy lejos (hay que pasar la prop por cinco niveles que no la usan), hay herramientas para compartir estado sin pasarlo a mano; aparecen cuando la aplicación crezca.

8.2 · Con qué se confunde

Con "un componente por cada cosa". Dividir en muchos componentes no es lo mismo que separar lógica de presentación: diez componentes que guardan cada uno su copia de los datos están divididos, pero no separados. La pregunta no es cuántos componentes hay, sino dónde vive cada dato y quién lo puede cambiar.

8.3 · Variantes y casos límite

  • Pasar la función set… directamente (onReservar={setIdElegida}) sirve cuando el hijo la llama justo con el valor que hay que guardar. Si la decisión tiene más pasos, se escribe una función propia (confirmarReserva).
  • Guardar el id y no el objeto. Si se guardara la clase completa en idElegida, quedaría una segunda copia que no se entera de los cambios de listaClases: el formulario mostraría cupos viejos.

8.4 · Errores frecuentes

  • Uncaught ReferenceError: FormularioReserva is not defined: usaste un componente sin importarlo (paso 12).
  • Uncaught ReferenceError: reservar is not defined: borraste una función que JSX todavía usa (paso 11).
  • Uncaught TypeError: onReservar is not a function al hacer clic: el padre no pasó la prop, o la pasó con otro nombre (onReserva), y el hijo la llama dentro de otra función.
  • Un clic que no hace nada, sin error: el hijo hace onClick={onCambiar} y el padre no le pasó onCambiar (el 🔬 del paso 9).
  • Dos componentes muestran datos distintos: cada uno tiene su propio useState con la misma información. Se corrige dejando un solo estado en el ancestro común.

8.5 · En un sistema real

Separar así hace que los componentes de presentación sean fáciles de probar (mismas props → misma pantalla) y de reutilizar. Es la idea de responsabilidad única (la S de SOLID): cada pieza tiene una sola razón para cambiar. TarjetaClase cambia si cambia el diseño de la tarjeta; las reglas de reserva cambian solo en App.

Concepto · formulario

React conoce cada letra

9.1 · Para qué existe

Un <input> de HTML guarda lo que escribes dentro de sí mismo. Mientras nadie más necesite ese texto, no hay problema. Pero un formulario sí lo necesita: hay que revisarlo antes de aceptarlo, mostrar un error si está mal y dejar los campos limpios después.

Si el texto vive solo en el campo, cada una de esas cosas obliga a ir a buscarlo en la página. Y hay otro problema: un formulario de HTML, al enviarse, recarga la página por su cuenta, y con eso se pierde todo lo que la aplicación tenía en memoria.

9.2 · Qué es

  • Definición técnica: un es un <input> cuyo valor lo decide el estado de React: value={nombre} dice qué se muestra y onChange actualiza el estado con lo que se escribe (setNombre(evento.target.value)). Un formulario controlado maneja su envío con onSubmit, cancela el envío del navegador con evento.preventDefault() y trabaja con los valores del estado. Validar es revisar esos valores con reglas antes de aceptarlos y decir qué falló.
  • Explicación sencilla: el campo ya no guarda nada: cada letra pasa por el estado, y el estado le dice al campo qué mostrar. Como React siempre sabe qué hay escrito, puede revisarlo, mostrar un error o limpiarlo cuando quiera.
  • En la vida real: la inscripción que llena la recepcionista mientras tú dictas. Lo que vale es lo que está en la planilla, no lo que dijiste. Antes de pasar la hoja, ella revisa que el nombre no esté vacío; si algo falla, te lo dice en ese momento.

Límites · formulario

Validar sin duplicar la verdad

13.1 · Cuándo no usarlo

  • Formularios muy grandes: un estado por campo se vuelve pesado; se usa un objeto, campos no controlados o una librería.
  • La validación del navegador como única defensa: cualquiera puede saltársela desde las herramientas del navegador. El servidor siempre valida otra vez (Clase 3).

13.2 · Con qué se confunde

Con la validación nativa de HTML (required, type="email", minLength).

Validación nativa de HTMLValidación con validarReserva
Quién la haceEl navegadorNuestro código
MensajesGlobos del navegador, en su idiomaLos que decidimos, debajo de cada campo
¿Se puede probar sola?NoSí: es una función

El punto donde chocan: un <input type="email"> dentro de un formulario hace que el navegador muestre su propio globo y no deje enviar. Por eso el formulario lleva noValidate.

13.3 · Variantes y casos límite

  • Espacios. " " tiene 3 caracteres pero ninguna letra. Por eso la regla usa trim() y lo que se guarda es el texto recortado.
  • Un solo estado para todo el formulario. const [datos, setDatos] = useState({ nombre: "", correo: "" }) y cada campo actualiza con setDatos({ ...datos, nombre: valor }). Con dos campos, dos estados se leen mejor.
  • Validar mientras se escribe. Se puede llamar validarReserva en cada onChange; suele molestar porque marca error desde la primera letra. Hoy se valida al enviar.

13.4 · Errores frecuentes

  • No se puede escribir y la consola advierte "You provided a value prop to a form field without an onChange handler.": falta onChange (el 🔬 del paso 19).
  • La página se recarga al confirmar: falta evento.preventDefault(), o el onSubmit está en el botón en lugar del <form> (el 🔬 del paso 17).
  • El campo muestra [object Object] al escribir: escribiste onChange={setNombre}; setNombre recibe el evento completo, no el texto. Se corrige con onChange={(evento) => setNombre(evento.target.value)}.
  • La reserva se hace aunque haya errores: validaste, pero falta el return cuando hay errores.

13.5 · En un sistema real

La validación del navegador es para ayudar a la persona a corregir rápido; la que protege el negocio es la del servidor, que en la Clase 3 responderá 422 si los datos no son válidos. Las reglas en una función pura (validarReserva) son fáciles de probar y de reutilizar: es la misma idea de responsabilidad única, ahora entre la regla y el componente que la muestra.

13.6 · Conexión

El formulario junta los tres conceptos: tiene estado propio (lo que se escribe), avisa a App como una pieza de presentación y valida con una función pura. Lo que queda abierto lo dijo Valeria en el fondo de su correo: si recarga la página, todo vuelve a empezar, y cada computador ve sus propios cupos. Eso lo resuelve un servidor (Clase 3).

16.1 · Las tres ideas de hoy

  1. El estado es la memoria de un componente. Se guarda con useState y se cambia entregando un valor nuevo con su función set…; así React se entera y vuelve a pintar. Vale igual para un contador de vasos, un parqueadero o un carrito de compras.
  2. Un lugar decide y los demás muestran. El estado vive en el ancestro común de quienes lo necesitan; los componentes de presentación reciben datos por props y avisan con funciones.
  3. El formulario controlado guarda cada campo en el estado, se envía con onSubmit + preventDefault y una función pura valida antes de aceptar.

16.2 · La decisión técnica más importante

Lo que se escribe en el formulario se quedó en el formulario; las clases y las reservas subieron a App. No es gusto: el texto que se escribe solo le importa al formulario, mientras que las clases y las reservas las necesitan varios componentes. El estado vive lo más cerca posible de quien lo usa.
